## Activity 1: AI-Generated OOP Version

### Design & Paradigm Philosophy
The AI generated the Object-Oriented cart based on classical OOP patterns:
- **Encapsulated State:** The internal collection of items (`#items`) lives within the instance across calls.
- **In-Place Mutation:** Methods (`addItem`, `removeItem`) mutate internal memory in place (`push`, `splice`).
- **Habit of Thought:** The cart is an active entity that holds data and knows how to act on it.

### Code Snippet: AI-Generated OOP Cart ([`oopCart.js`](https://github.com/Abdullah-Developer68/SDC-LAB-6/blob/main/oopCart.js))
```javascript
// Generated by AI Assistant
import { createItem } from './item.js';

export class ShoppingCart {
  static DISCOUNT_THRESHOLD = 100.0;
  static DISCOUNT_RATE = 0.10; // 10% discount above $100

  #items; // Private field protects internal collection from outside tampering

  constructor() {
    this.#items = [];
  }

  addItem(name, price) {
    this.#items.push(createItem(name, price));
  }

  removeItem(name) {
    const index = this.#items.findIndex(item => item.name === name);
    if (index !== -1) {
      this.#items.splice(index, 1);
      return true;
    }
    return false;
  }

  total() {
    const subtotal = this.#items.reduce((sum, item) => sum + item.price, 0);
    if (subtotal > ShoppingCart.DISCOUNT_THRESHOLD) {
      return subtotal * (1.0 - ShoppingCart.DISCOUNT_RATE);
    }
    return subtotal;
  }

  get count() {
    return this.#items.length;
  }
}
```

## Activity 2: Human-Crafted Functional Version & AI Critique

### Human Developer Review: Catching the AI's "Impure Functional" Trap
When asked to convert OOP code to functional style, AI models commonly generate functions that operate on standard mutable arrays (`array.push()` or returning mutable arrays). As highlighted in the pre-lab briefing:
> *"Review the difference between mutable and immutable data structures before class — the functional half of this exercise depends on recognising when the model's 'functional' code is not actually pure."*

The human developer caught this flaw and hand-crafted a **strictly pure functional implementation**:
1. **Guaranteed Immutability:** Enforced via `Object.freeze()`. Any accidental mutation throws a `TypeError` in strict mode.
2. **Pure Transformations:** Splicing is replaced by non-destructive operations (`spread`, `slice`, and `reduce`).
3. **Referential Transparency:** Functions depend purely on their inputs with zero side-effects.

### The Two Core Paradigm Differences Confirmed by Human Audit
1. **No In-Place Mutation:** Every write operation returns a new frozen array snapshot without altering the previous cart in memory.
2. **Elimination of Shared-Reference Aliasing Bugs:** In OOP, sharing an object instance between two variables (`cartB = cartA`) creates hidden coupling where mutating `cartB` mutates `cartA`. In FP, immutable data structures make shared-reference corruption impossible.

### Code Snippet: Human-Crafted Functional Cart ([`functionalCart.js`](https://github.com/Abdullah-Developer68/SDC-LAB-6/blob/main/functionalCart.js))
```javascript
// Hand-crafted by Human Developer
import { createItem } from './item.js';

export const DISCOUNT_THRESHOLD = 100.0;
export const DISCOUNT_RATE = 0.10;

export function createCart() {
  return Object.freeze([]);
}

export function addItem(cart, name, price) {
  const newItem = createItem(name, price);
  return Object.freeze([...cart, newItem]);
}

export function removeItem(cart, name) {
  const index = cart.findIndex(item => item.name === name);
  if (index === -1) return cart;
  return Object.freeze([...cart.slice(0, index), ...cart.slice(index + 1)]);
}

export function calculateTotal(cart) {
  const subtotal = cart.reduce((sum, item) => sum + item.price, 0);
  if (subtotal > DISCOUNT_THRESHOLD) {
    return subtotal * (1.0 - DISCOUNT_RATE);
  }
  return subtotal;
}
```

2. **Single Item:** Item at `$45.50` produces `$45.50` (no discount).

## Activity 4: Name the Trade-Off Honestly (Concrete Extension Example)

> *"The OOP version was faster to extend with a new feature that needs to remember cart-wide state across many calls (a running discount-code history, say). The functional version was easier to reason about in isolation every function's output depends only on its input, so a unit test never needs to worry about what happened in a previous test. Neither claim is universal; both are true for this specific 30-line example."*

### Code Comparison: [`tradeoffExtension.js`](https://github.com/Abdullah-Developer68/SDC-LAB-6/blob/main/tradeoffExtension.js)

#### 1. OOP Extension (AI Model): Stateful In-Place Accumulation
```javascript
export class ExtendedOOPCart {
  #items = [];
  #discountHistory = []; // Added in-place

  applyDiscountCode(code) {
    if (ExtendedOOPCart.CODE_DISCOUNTS[code] && !this.#discountHistory.includes(code)) {
      this.#discountHistory.push(code);
      return true;
    }
    return false;
  }

  total() {
    const subtotal = this.#items.reduce((sum, item) => sum + item.price, 0);
    let discountRate = subtotal > 100.0 ? 0.10 : 0.0;
    for (const code of this.#discountHistory) {
      discountRate += ExtendedOOPCart.CODE_DISCOUNTS[code] || 0.0;
    }
    return subtotal * (1.0 - Math.min(discountRate, 0.50));
  }
}
```

#### 2. Functional Extension (Human Model): Explicit State Snapshotting
```javascript
export function createExtendedCart() {
  return Object.freeze({
    items: Object.freeze([]),
    discountHistory: Object.freeze([])
  });
}

export function applyDiscountCodeExt(state, code) {
  if (CODE_DISCOUNTS[code] && !state.discountHistory.includes(code)) {
    return Object.freeze({
      items: state.items,
      discountHistory: Object.freeze([...state.discountHistory, code])
    });
  }
  return state;
}

export function calculateTotalExt(state) {
  const subtotal = state.items.reduce((sum, item) => sum + item.price, 0);
  let discountRate = subtotal > 100.0 ? 0.10 : 0.0;
  for (const code of state.discountHistory) {
    discountRate += CODE_DISCOUNTS[code] || 0.0;
  }
  return subtotal * (1.0 - Math.min(discountRate, 0.50));
}
```

## Core Evaluation: Simplicity, Reliability & Efficiency

| Attribute | Object-Oriented Programming (AI Model) | Functional Programming (Human Model) | Evaluation & Verdict |
| :--- | :--- | :--- | :--- |
| **Simplicity** | **High Syntactic Simplicity:** Very low ceremony for state accumulation. Adding the promo feature required adding one line to the constructor and mutating in place. Callers do not need to juggle state between function calls. | **High Cognitive Simplicity:** Each function is an isolated black box with zero hidden variables. However, requires explicit compound state container plumbing (`CartState: { items, discountHistory }`). | **OOP** is simpler for rapid state accumulation; **FP** is simpler for local component understanding. |
| **Reliability** | **Moderate:** Prone to **temporal coupling** (order-of-calls bug) and **aliasing hazards** (mutating `cartB` silently mutates `cartA`). | **Very High:** Complete immunity to side-effects and reference aliasing via `Object.freeze()`. Every test runs in pristine isolation with no shared leaks. | **FP wins decisively on reliability.** Immutability eliminates an entire class of production bugs. |
| **Efficiency** | **Very High:** Mutates arrays in-place (`push`, `splice`) without re-allocation. Extremely low garbage collection overhead. | **Moderate:** Spreading arrays (`[...cart, item]`) allocates new arrays and frozen wrappers on every modification, creating GC churn at extreme scale. | **OOP wins on raw computational efficiency** in unoptimized JavaScript runtimes. |

### Architectural Conclusion
- **Use OOP when:** Developing stateful UI controls, game physics entities, and high-frequency systems where avoiding memory allocations is critical.
- **Use Functional Programming when:** Developing financial calculations, payment processors, tax rules, audit trails, and concurrent request pipelines where state corruption and temporal bugs cannot be tolerated.
